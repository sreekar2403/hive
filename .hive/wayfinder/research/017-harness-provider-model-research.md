## opencode

- **Providers**: opencode ships with a `provider` map in `opencode.json`. Each entry specifies an `npm` package (the Vercel AI SDK provider, e.g. `@ai-sdk/anthropic`, `@ai-sdk/openai`, `@ai-sdk/google`, or the generic `@ai-sdk/openai-compatible`), optional `name`, `options` (`baseURL`, `apiKey` — supports `{env:VAR}` interpolation, `headers`), and a `models` map of model ids to metadata. Source: [opencode.ai/docs/providers/](https://opencode.ai/docs/providers/).
- **Model selection**: `opencode run [message..]` is the CLI entry point (e.g. `opencode run --attach http://localhost:4096 "Explain async/await in JavaScript"`, per the docs' own example). The `--model`/`-m` flag documentation explicitly states the value must be in the form `provider_id/model_id`, matching the same shape used in config — no bare model-id support. Source: [opencode.ai/docs/cli/](https://opencode.ai/docs/cli/) (fetched directly) and corroborated via [OpenCode Providers docs mirror](https://open-code.ai/en/docs/providers) and [Models docs](https://opencode.ai/docs/models/) found in search.
- **Local backends**: Because `@ai-sdk/openai-compatible` is just another `npm` provider package, Ollama, LM Studio, and llama.cpp's OpenAI-compatible server (`llama-server`) are configured identically to any other vendor — only the `baseURL` differs:
  - Ollama: `http://localhost:11434/v1`
  - LM Studio: `http://127.0.0.1:1234/v1`
  - llama.cpp (`llama-server`): `http://127.0.0.1:8080/v1`

  This means opencode's provider abstraction is genuinely generic — Hive does not need a separate direct-to-local path for opencode-routed tasks; it only needs to know to write/point an `opencode.json` provider entry with the right `baseURL` and treat that provider id as "local."

## claude-code (`claude` CLI)

- **Model flag**: `claude --model <alias-or-full-name>` — aliases `sonnet`, `opus`, `haiku`, `fable`, or a full id (`claude-sonnet-5`). Confirmed to override both the `model` setting and the `ANTHROPIC_MODEL` env var, and confirmed to work with `-p` (print/non-interactive mode). Also `--fallback-model <model1>,<model2>,...` (also works with `-p`). Source: [code.claude.com/docs/en/cli-reference](https://code.claude.com/docs/en/cli-reference).
- **settings.json**: has a top-level `model` key (read once at session start; requires restart), `availableModels`/`enforceAvailableModels` to restrict the picker, `modelOverrides` (map model id → Bedrock/Vertex ARN or id), and an `env` block that can carry any of the env vars below without exporting them in the shell. Source: [code.claude.com/docs/en/settings](https://code.claude.com/docs/en/settings), [code.claude.com/docs/en/amazon-bedrock](https://code.claude.com/docs/en/amazon-bedrock).
- **Bedrock / Vertex**: `CLAUDE_CODE_USE_BEDROCK=1` (+ `AWS_REGION`, standard AWS credential chain, optional `CLAUDE_CODE_USE_MANTLE=1` for the native-Anthropic-shape "Mantle" endpoint) and `CLAUDE_CODE_USE_VERTEX=1` (+ `CLOUD_ML_REGION`, `ANTHROPIC_VERTEX_PROJECT_ID`, GCP Application Default Credentials) are both confirmed, officially documented, first-party alternate-cloud-provider mechanisms. Sources: [code.claude.com/docs/en/amazon-bedrock](https://code.claude.com/docs/en/amazon-bedrock), [code.claude.com/docs/en/google-vertex-ai](https://code.claude.com/docs/en/google-vertex-ai).
- **`ANTHROPIC_BASE_URL` / `ANTHROPIC_AUTH_TOKEN` / `ANTHROPIC_API_KEY`**: `ANTHROPIC_BASE_URL` is explicitly documented as "the variable that points Claude Code at the gateway," i.e. an officially supported override, but it is scoped and intended for "LLM gateways" that speak the Anthropic protocol — the docs explicitly say Anthropic "doesn't endorse, maintain, or audit third-party gateway products, and doesn't support routing Claude Code to non-Claude models through any gateway." So it's an official mechanism, but pointing it at a local Ollama/LM Studio instance is outside Anthropic's supported use case, even though it works. Source: [code.claude.com/docs/en/llm-gateway](https://code.claude.com/docs/en/llm-gateway).
- **Ollama native Anthropic compatibility**: Ollama v0.14.0+ added Anthropic Messages API compatibility (confirmed date around 2026-01-16 per Ollama's own blog post). Setup: `ANTHROPIC_AUTH_TOKEN=ollama` + `ANTHROPIC_BASE_URL=http://localhost:11434`, then e.g. `claude --model gpt-oss:20b`. Source: [ollama.com/blog/claude](https://ollama.com/blog/claude).
- **LM Studio native Anthropic compatibility**: LM Studio 0.4.1 (released 2026-01-30, confirmed via LM Studio's own changelog, which lists "New: Anthropic API compatibility endpoint: `/v1/messages`" — "Use Claude Code with LM Studio") introduced a native `/v1/messages` endpoint. Setup: start the server (`lms server start --port 1234`), then `ANTHROPIC_BASE_URL=http://localhost:1234` + `ANTHROPIC_AUTH_TOKEN=lmstudio`, then e.g. `claude --model openai/gpt-oss-20b`. Sources: [lmstudio.ai/blog/claudecode](https://lmstudio.ai/blog/claudecode), [lmstudio.ai/changelog/lmstudio-v0.4.1](https://lmstudio.ai/changelog/lmstudio-v0.4.1).
- **Net effect for Hive**: claude-code has no generic "OpenAI-compatible provider" concept the way opencode does — it only ever speaks the Anthropic wire protocol. Local support is real and functions end-to-end, but it depends on (a) the local server having built an Anthropic-shaped endpoint (not all local servers have — this is Ollama/LM Studio specific, not a llama.cpp guarantee) and (b) Hive redirecting via env vars (`ANTHROPIC_BASE_URL`/`ANTHROPIC_AUTH_TOKEN`) rather than a `--model provider/model` style flag.

## pi

- **CLI flags**: `--provider <name>` selects a built-in provider (`anthropic`, `openai`, `google`, etc. — pi keeps a refreshable list of tool-capable models per provider via `pi update --models`); `--model <pattern>` accepts a model id/pattern, including `provider/id` form and an optional `:<thinking>` reasoning suffix; `--api-key <key>` overrides credentials. Mid-session switching via `/model` or Ctrl+L. Source: [github.com/earendil-works/pi — packages/coding-agent/README.md](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/README.md).
- **Custom providers (`~/.pi/agent/models.json`)**: documented as the place to "add providers... if they speak a supported API (OpenAI, Anthropic, Google)." Confirmed schema fields (from the coding-agent docs) include a `providers` map keyed by provider id, each with `baseUrl`, `apiKey` (supports `$ENV_VAR` interpolation), `api` (e.g. `"openai-completions"`), and a `models[]` array with per-model metadata (`id`, `name`, `reasoning`, `input`, `cost`, `contextWindow`, `maxTokens`). This is the path by which Ollama or LM Studio's _generic OpenAI-compatible_ endpoint (`http://localhost:11434/v1`, `http://localhost:1234/v1`) would be added, exactly like any other OpenAI-compatible cloud vendor. For anything beyond the three built-in wire protocols (custom auth flows, OAuth), pi expects an extension registering via `pi.registerProvider()`. Source: docs/custom-provider.md in the pi repo (fetched via GitHub raw content).
- **Bundled llama.cpp integration — the crux finding**: pi ships a **separate, first-party local-inference feature** distinct from the generic `models.json` provider path. It's reached with `/login llama.cpp`, which prompts for a router URL (default `http://127.0.0.1:8080`) and optional API key, configurable via `LLAMA_BASE_URL`/`LLAMA_API_KEY` env vars. The `/llama` command manages the model lifecycle: browsing/downloading models from Hugging Face by `owner/repository[:quant]` (the llama.cpp server process does the actual download; `HF_TOKEN` is used for gated repos), loading/unloading models, and inspecting router state — pi explicitly does not silently unload or delete models. Once a model is loaded, `/model` selects it for the session. This is documented separately at `docs/llama-cpp.md` in the pi repo, distinct from `docs/custom-provider.md`. Source: [github.com/earendil-works/pi — packages/coding-agent/docs/llama-cpp.md](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/llama-cpp.md).
- **Net effect for Hive**: pi gives you _both_ routes to local models — generic OpenAI-compatible provider config (works for Ollama/LM Studio, same shape as cloud) and a bundled, purpose-built llama.cpp router with its own model-download/lifecycle UX. Neither requires Hive to build its own direct-to-local path, but Hive's config/UI needs to distinguish which of the two a given pi task is using, since they have different config surfaces (`models.json` entries vs. `/login llama.cpp` + `LLAMA_BASE_URL`/`LLAMA_API_KEY` + `/llama` model management) and different failure/VRAM implications (the llama.cpp router directly loads/unloads local model weights, which is exactly the kind of VRAM-relevant state ticket 024's queue design cares about).

## Gap for Hive's implementation

None of the three current harness wrapper classes actually pass a `--model` flag to the spawned process:

- `packages/server/src/harnesses/opencode.ts` — spawns `opencode run --pure --format json <prompt>`. No `--model` flag; the constructor's `_model` field (default `'sonnet'`) is stored but never placed on the command line.
- `packages/server/src/harnesses/claudeCode.ts` — spawns `claude -p <prompt> --output-format json`. No `--model` flag; same inert `_model` field.
- `packages/server/src/harnesses/pi.ts` — spawns `pi -p <prompt>`. No `--model` (and no `--provider`) flag at all; same inert `_model` field.

Combined with `packages/server/src/config.ts`, which only stores a single flat `defaultModel: string` per harness (no `provider` field) and `packages/server/src/router.ts`, which routes on harness + bare model string only, this means:

1. Today, whichever model each CLI's own default/session settings.json/opencode.json resolve to is what actually runs — Hive's per-task `defaultModel` config is not enforced at the process level for any of the three harnesses.
2. There is no `provider` dimension anywhere in Hive's config or routing today, even though all three harnesses genuinely have one (opencode natively; claude-code via env-var redirection; pi via `--provider`/`models.json`/llama.cpp). Ticket 021 (Settings) and 024 (VRAM-aware queue) will need to add a provider field (and, for claude-code specifically, a base-URL/auth-token override surface rather than a flag) alongside the harness+model fields that exist today.
3. To make local-model routing observable to the VRAM-aware queue (024), Hive needs each harness invocation to carry an explicit "local" signal — for opencode/pi this can be a provider id lookup (is the configured provider's `baseURL` a loopback address, or for pi is it the llama.cpp router specifically); for claude-code it has to be based on whether `ANTHROPIC_BASE_URL` is being overridden to a loopback address, since there is no provider concept to inspect.
